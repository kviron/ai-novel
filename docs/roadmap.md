# Дорожная карта AI Visual Novel

Дата актуализации: 2026-09-25
Статус проекта: первый вертикальный срез реализован; смежные функции развиваются небольшими проверенными срезами
Главная спецификация: [`superpowers/specs/2026-09-18-ai-visual-novel-platform-design.md`](superpowers/specs/2026-09-18-ai-visual-novel-platform-design.md)

## 1. Назначение

Эта дорожная карта определяет порядок развития локальной русскоязычной платформы AI-визуальных новелл. Она отвечает на три вопроса:

1. Какой законченный результат получает пользователь на каждом этапе?
2. Какие архитектурные возможности должны появиться раньше других?
3. По каким проверяемым критериям этап считается завершённым?

Карта не заменяет спецификации и implementation plans. Для каждого этапа сначала уточняется отдельная спецификация, затем создаётся исполнимый план с файлами, контрактами, тестами и небольшими задачами.

## 2. Правила ведения

### Статусы

- `planned` — границы этапа определены, но отдельная спецификация ещё не утверждена;
- `specified` — спецификация утверждена;
- `ready` — implementation plan утверждён, зависимости выполнены;
- `in_progress` — идёт реализация;
- `verification` — функциональность собрана, выполняются проверки и ревью;
- `done` — выполнены все критерии готовности, документация обновлена;
- `blocked` — зафиксирована конкретная внешняя зависимость, без которой нельзя продолжить.

### Переход этапа в `done`

Этап завершается только когда:

- пользовательский сценарий работает целиком, а не набором несвязанных экранов или API;
- схема данных изменена миграцией и проверена на существующей базе;
- публичные интерфейсы описаны и покрыты contract tests;
- backend, frontend, lint, typecheck, build и относящиеся к этапу E2E проходят;
- русские состояния ошибок имеют понятное действие восстановления;
- критические решения и ограничения отражены в спецификации;
- дорожная карта обновлена свежим статусом и ссылками на фактические документы.

### Правила изменения приоритетов

1. Сначала устраняются блокеры текущего пользовательского сценария.
2. Архитектурная подготовка выполняется только для ближайшего этапа, а не «на будущее».
3. Новая абстракция появляется при второй реальной реализации или доказанной сменяемой границе.
4. Исследования моделей, лицензий и производительности не смешиваются с продуктовой реализацией: результат исследования — решение с измерениями.
5. Незавершённый этап не расширяется новой большой возможностью; она помещается в следующий этап или отдельный spike.

| 3. Два режима новеллы | `planned` | Спецификация setup свободной и гибридной игры |

| 6. Полноэкранные CG | `planned` | Benchmark открытых моделей изображений |
| 7. GPU-задания и ComfyUI | `planned` | Контракт ImageProvider и устойчивой очереди |
| 8. LoRA персонажей | `planned` | Исследование trainer и контрольной матрицы |
| 9. Провайдеры и смена LLM | `planned` | Смена установленной Ollama-модели работает; далее capability contract и другие провайдеры |

| 12. Упаковка и релиз | `planned` | Решение по desktop runtime и обновлениям |

Промежуточная работа после этапа 1: реализованы глобальная навигация, библиотека с серверными автосохранениями, глобальный каталог персонажей, авторская тестовая студия, откат до 10 ходов с сохранением прежних ветвей, смена установленной Ollama-модели между ходами и два фона тестовой истории. Каталог показывает Аканэ и Марка с отдельными портретами, профилями и фильтром по полу. Профили перенесены в неизменяемые ревизии; автор теперь может создать персонажа и новую ревизию в каталоге, а в отдельном экране состава новеллы закрепить выбранную ревизию. Сессии сохраняют версию, выбранную на момент запуска. Игровая сцена адаптирована к узким экранам, поддерживает режим скрытого интерфейса и внутреннюю прокрутку инспектора. См. [спецификацию общей оболочки](superpowers/specs/2026-09-24-global-app-shell-design.md), [спецификацию переносимых персонажей](superpowers/specs/2026-09-24-portable-characters-design.md) и [аудит MVP](architecture/mvp-audit-2026-09-24.md). Остальные этапы ещё не завершены.

## 5. Этапы

### Этап 1. Первый игровой цикл с Ollama

**Статус:** `done`
**Пользовательский результат:** игрок запускает встроенную гибридную историю с Аканэ, выбирает вариант или пишет действие, получает проверенный ответ локальной модели, видит подтверждённый спрайт и продолжает после перезапуска приложения.

**Входит:**

- SQLModel, Alembic и безопасная миграция существующей SQLite;
- встроенная история и сохраняемая игровая сессия;
- базовый каталог с обложкой и описанием, список начатых прохождений из SQLite с продолжением по ID сессии (реализовано после первого среза; слоты и облачная синхронизация относятся к следующим этапам);
- `LLMProvider` и Ollama;
- структурированный `TurnProposal`, repair и серверные правила;
- идемпотентный атомарный ход и optimistic concurrency;
- минимальный FSD frontend;
- блокировка управления при недоступности Ollama;
- unit, component и E2E проверки критического пути.

**Не входит:** каталог персонажей, rollback, CG, LoRA, ComfyUI, OpenAI и редактор сюжетов.

**Контракт:** SQLite и story engine являются источником истины; LLM только предлагает ход. Ошибка или непроверяемый ответ не меняют состояние. Один успешный запрос создаёт один ход и увеличивает `state_version` на один.

**Обязательные навыки:** `fastapi`, `feature-sliced-design`, `shadcn`, `test-driven-development`, `playwright`, `verification-before-completion`.

**Критерии готовности:** совпадают с Definition of Done утверждённого implementation plan.

**Проверено:** `npm run check` (33 frontend и 82 backend теста, lint, typecheck, build) и `npm run test:e2e` (один игровой цикл с перезагрузкой через локальный fake Ollama); миграция старой SQLite и контракты API покрыты backend тестами.

**Документы:**

- [Спецификация платформы](superpowers/specs/2026-09-18-ai-visual-novel-platform-design.md)
- [План первого игрового цикла](superpowers/plans/2026-09-18-first-playable-ollama-slice.md)

### Этап 2. Каталог и переносимые персонажи

**Статус:** `done`
**Зависит от:** этапа 1  
**Пользовательский результат:** пользователь создаёт персонажа один раз, хранит его в каталоге, добавляет в разные новеллы и при необходимости извлекает нового персонажа из прохождения.

**Реализовано:** глобальный каталог, отдельная страница профиля и редактор, стабильные ID и неизменяемые ревизии, привязка персонажа к разным новеллам с ролью и цветом. История и сессия читают закреплённые ревизии; старые прохождения не меняются при обновлении каталога. Из прохождения можно извлечь независимый профиль. Аватар и обложка с происхождением, лицензией и SHA-256 закреплены за ревизией. ZIP-экспорт и повторный импорт переносят текстовые ревизии и материалы без секретов провайдеров. Движок хранит упорядоченные фрагменты повествования и речи нескольких персонажей и проверяет очевидное дублирование реплик.

**Входит:**

- глобальная сущность персонажа и неизменяемые ревизии;
- аватар, обложка, описание, биография, внешность и взрослый возраст;
- роли и переопределения персонажа внутри конкретной новеллы;
- provenance, лицензия и хеш каждого материала;
- import/export manifest без секретов провайдеров;
- каталог, просмотр и редактор базовых данных персонажа.

**Не входит:** генерация новых спрайтов, LoRA, автоматическое обучение и сложный сюжетный граф.

**Контракт:** новелла ссылается на конкретную ревизию персонажа. Редактирование каталога создаёт новую ревизию и не меняет уже начатые прохождения. Извлечение из новеллы создаёт независимый каталоговый объект с сохранённым происхождением.

**Обязательные навыки:** `brainstorming`, `writing-plans`, `philosophy-of-software-design`, `fastapi`, `feature-sliced-design`, `security-best-practices`.

**Критерии готовности:** персонаж переносится между двумя тестовыми новеллами; старая сессия воспроизводит прежнюю ревизию; экспорт и повторный импорт не теряют материалы и происхождение.

**Контракт архива:** [формат ZIP и хранение материалов](architecture/character-archive.md); [спецификация этапа](superpowers/specs/2026-09-25-portable-character-materials-design.md), [план реализации](superpowers/plans/2026-09-25-portable-character-materials.md).

**Проверка:** 2026-09-25 — 80 фронтенд-тестов, 135 бэкенд-тестов, 13 E2E, lint/typecheck/build; миграция существующей SQLite до `20260925_11` с сохранением новеллы и 14 сессий.

### Этап 3. Свободная и гибридная новеллы

**Статус:** `planned`  
**Зависит от:** этапов 1–2  
**Пользовательский результат:** перед началом игрок выбирает свободную или авторскую новеллу, описывает либо выбирает героя и получает понятные границы доступной свободы.

**Входит:**

- режим `freeform` с жанром, настроением, героем и предысторией;
- режим `hybrid` с каноном, обязательными событиями и свободными действиями;
- политики героя: фиксированный, созданный игроком или выбранный из каталога;
- story setup flow и предварительный просмотр настроек;
- версия правил генерации, закреплённая в сессии.

**Не входит:** визуальный редактор графа, полноценная долговременная память и облачные модели.

**Контракт:** режим является явным свойством версии новеллы. Свободный режим всё равно использует проверяемое каноническое состояние; гибридный режим не позволяет модели отменять authored-факты и обязательные события.

**Критерии готовности:** два E2E-сценария стартуют с разными политиками героя; гибридная модель отклоняет нарушение канона; свободная новелла формирует воспроизводимое начальное состояние.

### Этап 4. Память, сохранения и временная линия

**Статус:** `planned`  
**Зависит от:** этапа 1; интегрируется с этапом 3  
**Пользовательский результат:** игрок сохраняется, откатывает ход, создаёт альтернативную ветку и продолжает длинную историю без потери ключевых фактов.

**Реализованный первый срез:** SQLite хранит одно активное автосохранение на новеллу, до 10 последовательных откатов и неизменяемые ходы с родительскими связями. После нового действия прежняя ветка остаётся в базе, а контекст модели строится только по активной ветке. Ручные слоты, карта веток, summaries и метапрогресс остаются в плане.

**Входит:**

- неизменяемые checkpoints и указатель текущей ветки;
- автосохранения, ручные и быстрые слоты;
- rollback и новая ветка после альтернативного действия;
- история реплик и повторная генерация как ветвление;
- слои памяти, summaries и ссылки на факты-источники;
- отдельный постоянный метапрогресс.

**Не входит:** синхронизация между устройствами и облачное резервное копирование.

**Контракт:** прошлый checkpoint не изменяется. Откат двигает указатель, а новое действие создаёт ветку. Summary ускоряет контекст, но не заменяет исходные ходы и не становится фактом без проверки.

**Критерии готовности:** ветви расходятся без потери общего прошлого; save/load воспроизводит одинаковое состояние; метапрогресс не откатывается; конфликтующие summaries обнаруживаются тестом.

### Этап 5. Расширяемые визуальные состояния и спрайты

**Статус:** `planned`  
**Зависит от:** этапа 2  
**Пользовательский результат:** автор или пользователь добавляет персонажу новую эмоцию, позу или костюм, описывает условия применения и получает согласованный спрайт.

**Реализованный первый срез:** движок проверяет стабильные IDs двух костюмов тестовой истории; у Аканэ есть лист эмоций, у Марка пока только портретная подстановка в сцене. Два аниме-фона выбираются по подтверждённой визуальной директиве хода. Редактора и утверждения новых материалов нет.

**Входит:**

- нормализованные `emotion`, `pose`, `outfit` и совместимые комбинации;
- описание значения состояния и условий использования;
- материал состояния, crop/anchor/scale и прозрачность;
- preview → review → approve workflow;
- fallback при отсутствии точной комбинации;
- UI управления визуальными состояниями.

**Не входит:** обучение LoRA и произвольная генерация CG во время игрового хода.

**Контракт:** LLM выбирает только стабильные IDs из разрешённого набора. Пути, координаты и формат файла скрыты внутри visual-state модуля. Новый материал становится доступен игре только после утверждения.

**Критерии готовности:** новая эмоция создаётся, проверяется и используется в следующем ходе; несовместимая комбинация отклоняется; fallback не искажает пропорции персонажа.

### Этап 6. Полноэкранные CG-сцены и галерея

**Статус:** `planned`  
**Зависит от:** этапа 5  
**Пользовательский результат:** важные сцены показываются цельным полноэкранным артом с несколькими взаимодействующими персонажами вместо наложения обычных спрайтов.

**Сначала выполняется benchmark:** FLUX.2 Klein Base 4B, FLUX.2 Klein 4B distilled, Z-Image 6B и выбранный SDXL anime baseline на RTX 5080 16 ГБ.

**Входит:**

- одинаковая матрица prompt/seed/reference для сравнения;
- сцены с одним и двумя персонажами, близким взаимодействием, динамикой, кровью и допустимым взрослым контентом;
- контроль идентичности, рук, композиции, VRAM, времени и лицензий;
- `cg_scene` directive, placeholder и галерея открытых CG;
- ручное утверждение финального результата.

**Не входит:** автоматическое обучение LoRA и облачная генерация изображений.

**Контракт:** решение о модели принимается по измерениям и лицензии. CG имеет стабильный ID, provenance, prompt/workflow version и связь с checkpoint; неудачная генерация не блокирует сохранённый текстовый ход.

На этом этапе CG-модель, галерея и игровой показ проверяются на заранее подготовленных результатах benchmark. Запуск тяжёлой генерации из приложения становится пользовательской возможностью только после устойчивой очереди этапа 7.

**Критерии готовности:** выбран воспроизводимый pipeline; утверждённая CG открывается в сцене и галерее; fallback работает при отсутствии или ошибке изображения.

### Этап 7. ComfyUI и устойчивые GPU-задания

**Статус:** `planned`  
**Зависит от:** решения этапа 6  
**Пользовательский результат:** тяжёлые изображения создаются в фоне с видимым прогрессом, возможностью повтора и без зависания игрового API.

**Входит:**

- отдельный `ImageProvider` и адаптер ComfyUI;
- нормализованное задание вместо протекания workflow JSON;
- persistent queue со статусами `queued`, `running`, `review_required`, `approved`, `failed`, `cancelled`;
- отдельный worker, восстановление после перезапуска и диагностические метаданные;
- локальный GPU scheduler и приоритет активной игры.

**Не входит:** распределённая очередь и несколько GPU-хостов.

**Контракт:** FastAPI управляет заданиями, worker владеет длительным выполнением. Один GPU исполняет одну тяжёлую задачу; повтор использует новый attempt, но не теряет историю предыдущего.

**Критерии готовности:** очередь переживает перезапуск; отмена и повтор детерминированы; активный игровой запрос не конкурирует с обучением за VRAM.

---

### Этап 8. LoRA и постоянство внешности

**Статус:** `planned`  
**Зависит от:** этапов 2, 5 и 7  
**Пользовательский результат:** пользователь обучает версионированный визуальный профиль персонажа и получает узнаваемые спрайты и CG в разных сценах.

**Входит:**

- `TrainingProvider` и отдельный training worker;
- подготовка, подписи и проверка обучающего набора;
- base model, trigger phrase, параметры и версия LoRA;
- контрольная сетка ракурсов, эмоций, поз, одежды и взаимодействий;
- ручное утверждение версии и безопасный rollback профиля;
- метрики времени, VRAM и визуальной стабильности.

**Не входит:** автоматическое добавление сгенерированных изображений обратно в dataset и публикация моделей во внешние каталоги.

**Контракт:** обучение никогда не запускается внутри FastAPI. Неутверждённая LoRA не становится основной. Стиль новеллы, постоянные черты и сложный костюм могут быть разными адаптерами.

**Критерии готовности:** утверждённый профиль проходит фиксированную матрицу; переключение версии воспроизводимо; повреждённое или отменённое обучение не меняет активный профиль.

---

### Этап 9. Дополнительные LLM-провайдеры и смена модели

**Статус:** `planned`  
**Зависит от:** этапа 1; может развиваться параллельно этапам 2–8  
**Пользовательский результат:** игрок меняет совместимую модель между ходами и видит, какие данные будут отправлены локальному или облачному провайдеру.

**Реализованный первый срез:** новая сессия выбирает доступную локальную модель при недоступности рекомендованной; между ходами можно сменить установленную Ollama-модель без потери сессии, а каждый ход хранит использованную модель. Других провайдеров, профилей возможностей и облачных ключей нет.

**Входит:**

- capability metadata: schema, context, русский язык и категории контента;
- профили `narrative_fast`, `narrative_balanced`, `narrative_quality`;
- benchmark локальных моделей на едином русском наборе;
- OpenAI adapter через официальный API;
- системное хранение секретов для desktop-сборки;
- смена модели между ходами и фиксация фактической модели в каждом turn.

**Не входит:** использование подписки ChatGPT вместо API и незаметное перенаправление чувствительного контента в облако.

**Контракт:** смена модели применяется только к следующему ходу и не меняет канон. Несовместимая модель видна с объяснением, но недоступна для выбора. Секрет не хранится в SQLite, frontend, prompt или логах.

**Критерии готовности:** одна сессия продолжает историю двумя совместимыми моделями; provenance каждого хода точен; cloud consent и удаление ключа проверены; contract tests одинаковы для адаптеров.

### Этап 10. Сюжетный граф и инструменты автора

**Статус:** `planned`  
**Зависит от:** этапов 1 и 3; использует персонажей этапа 2  
**Пользовательский результат:** автор задаёт канон, события, условия, последствия и концовки, а затем проверяет достижимость истории до публикации.

**Реализованный первый срез:** студия запускает тестовую сессию текущей истории и показывает подтверждённое сервером состояние. Это ещё не редактор графа, lint или симулятор узлов.

**Входит:**

- versioned story graph со стабильными UUID;
- главы, события, условия, эффекты, обязательные точки и концовки;
- границы свободы ИИ и режиссёрские указания;
- lint недостижимых узлов, тупиков, циклов, ресурсов, типов и возрастных правил;
- simulator с переходом к узлу и изменением переменных;
- compatibility check версии истории и сохранения.

**Не входит:** совместное облачное редактирование несколькими авторами.

**Контракт:** authored graph хранит смысл и ограничения, а не весь сгенерированный текст. Runtime не редактирует опубликованную версию графа. Lint сообщает точный объект и способ исправления.

**Критерии готовности:** тестовая история имеет минимум две достижимые концовки; simulator воспроизводит обе; намеренно сломанные графы дают стабильные диагностические коды.

---

### Этап 11. Режиссура, звук, чтение и доступность

**Статус:** `planned`  
**Зависит от:** стабильных игровых, временных и визуальных контрактов этапов 3–6  
**Пользовательский результат:** новелла ощущается полноценной постановкой: музыка, эффекты, переходы и управление чтением доступны без мыши и с учётом индивидуальных настроек.

**Входит:**

- независимые каналы music/SFX/voice;
- фон, свет, позиции, камера, переходы и эффекты;
- auto, skip read/all, backlog, hide UI и replay voice;
- централизованные русские UI strings и стабильные line IDs;
- клавиатура, focus, масштаб, contrast, reduced motion, TTS-ready text и alt descriptions;
- сохранение пользовательских настроек вне timeline rollback.

**Не входит:** обязательный voice cloning; он требует отдельного исследования согласия, качества и лицензий.

**Контракт:** режиссёрские эффекты не меняют каноническое состояние. Настройки скорости и reduced motion влияют на представление, но не блокируют управление или доступ к тексту.

**Критерии готовности:** критический путь полностью проходится клавиатурой; настройки переживают перезапуск; отключение эффектов не меняет сюжет; аудиоканалы регулируются независимо.

### Этап 12. Упаковка, защита данных и релиз

**Статус:** `planned`  
**Зависит от:** готовности выбранного продуктового набора этапов 1–11  
**Пользовательский результат:** приложение устанавливается, обновляется и восстанавливает локальные истории и материалы без ручной настройки среды разработки.

**Входит:**

- выбор и проверка desktop runtime;
- управление процессами FastAPI, worker, Ollama и ComfyUI;
- системное хранилище секретов;
- backup/restore и проверка целостности SQLite/assets;
- миграции при обновлении и совместимость сохранений;
- release build, подпись/хеши артефактов и русская диагностика;
- security review Python/FastAPI и TypeScript/React границ.

**Не входит:** обязательный облачный аккаунт и сбор пользовательского контента по умолчанию.

**Контракт:** пользовательские данные остаются локальными, пока пользователь явно не выбрал облачную операцию. Обновление не запускается без проверяемого пути восстановления. Удаление приложения не считается резервной копией данных.

**Критерии готовности:** установка на чистой системе проходит smoke test; обновление со старой БД сохраняет прохождения; backup восстанавливается; секреты и чувствительный контент отсутствуют в диагностическом bundle по умолчанию.

## 6. Сквозные направления

Эти требования не являются отдельными «финальными» этапами и применяются с первого изменения:

- **Русский язык:** UI, ошибки и первая новелла полностью русскоязычны.
- **Безопасность:** внешние входы валидируются; секреты изолируются; логирование чувствительного контента выключено по умолчанию.
- **Контент 18+:** только явно совершеннолетние персонажи; рейтинг и предупреждения проверяются до вызова провайдера.
- **Происхождение материалов:** источник, автор, лицензия и хеш сопровождают импортированные и созданные assets.
- **Доступность:** клавиатура, focus, reduced motion и масштабирование проверяются при создании каждого нового сценария UI.
- **Наблюдаемость:** ошибки имеют machine-readable code, correlation/request ID и безопасную диагностическую причину.
- **Миграции:** изменение хранимых данных всегда сопровождается forward migration и тестом сохранения существующих записей.
- **Производительность:** обычный игровой ход приоритетнее preview, финальной генерации и обучения.

## 8. Риски

| Риск | Ранний сигнал | Ответ |
|---|---|---|
| Разрастание первой версии | В Task 1 появляются CG, каталог или rollback | Вернуть работу к утверждённому DoD этапа 1 |
| LLM нарушает канон | Правила проверяются только prompt-ом | Проверять предложение story engine до commit |
| Потеря идентичности персонажа | Новые изображения принимаются автоматически | Review gate и фиксированная визуальная матрица |
| 16 ГБ VRAM недостаточно | Offload делает игровой UX неприемлемым | Разделить fast/quality profiles и сериализовать GPU jobs |
| Протекание ComfyUI в домен | API хранит workflow JSON | Нормализованный `ImageProvider` и versioned adapter |
| Слишком ранняя универсализация | Появляются пустые слои и generic services | YAGNI, второй реальный consumer до выделения abstraction |
| Несовместимые сохранения | Модель данных меняется без версии | Alembic, content/save versions и migration tests |
| Утечка взрослого контента или ключей | Полные prompts попадают в обычные логи | Safe logging defaults и security review на provider boundary |

## 9. Рабочий цикл Superpowers

Для каждого нового этапа используется одинаковый процесс:

```text
brainstorming
  → утверждённая спецификация
    → writing-plans
      → executing-plans или subagent-driven-development
        → TDD для каждой задачи
          → requesting-code-review
            → verification-before-completion
              → обновление этой дорожной карты
```

При неожиданном падении используется `systematic-debugging`; при завершении самостоятельной ветки — `finishing-a-development-branch`. Навыки FastAPI, FSD, shadcn, Playwright и security подключаются только в относящихся к ним задачах.
