# Архитектура AI Visual Novel

Дата: 2026-09-18  
Статус: на проверке  
Заменяет: `2026-09-16-ai-visual-novel-v01-design.md`

## 1. Цель продукта

Создать локальную русскоязычную платформу визуальных новелл, в которой авторский сюжет и генеративный ИИ могут сочетаться в разных пропорциях. Игрок должен получать полноценную визуальную новеллу: диалоги, выборы, свободные действия, музыку, звуки, спрайты, полноэкранные CG-сцены, сохранения, откат и галерею, а не только текстовый чат с изображением персонажа.

Платформа поддерживает два основных режима:

1. **Свободная новелла.** Игрок описывает героя, предысторию, жанр и настроение. ИИ создаёт мир, персонажей и развитие истории.
2. **Гибридная авторская новелла.** Автор задаёт мир, персонажей, сюжетные события, условия и границы свободы. ИИ ведёт сцену и принимает свободные действия игрока, но не может самовольно менять канон.

В одной новелле главный герой может быть фиксированным, созданным перед началом, выбранным из каталога пользователя либо любым из этих вариантов — по правилам автора.

## 2. Принципы

- SQLite и игровой движок являются источником истины; ответ модели — только предложение.
- ИИ-провайдеры заменяемы и не проникают в доменную модель.
- Обычный игровой ход должен быть быстрым; тяжёлая генерация изображений и обучение выполняются асинхронно.
- Каждый принятый ход является неизменяемой контрольной точкой временной линии.
- Персонажи и их визуальная идентичность версионируются и могут переноситься между новеллами.
- Русский язык является первым и полным языком интерфейса, но контент получает стабильные идентификаторы для будущей локализации.
- Архитектура начинается минимальной и расширяется только при появлении реального повторного использования.
- Проект учитывает проверенные практики Ren’Py, Ink и Yarn Spinner: save/load/rollback, постоянный метапрогресс, стабильные ID строк, разделение сценария и runtime-состояния, аудиоканалы, lint и симуляцию ветвей.

## 3. Границы и этапы

### Первый вертикальный этап

- гибридная тестовая история с Аканэ;
- один локальный пользователь;
- Ollama как первый LLM-провайдер;
- готовые варианты и свободное действие;
- структурированный ответ модели и серверная валидация;
- сохранение ходов и восстановление прохождения в SQLite;
- выбор существующих спрайтов;
- блокировка управления при недоступности Ollama;
- перенос текущего интерфейса на минимальную FSD-структуру;
- серверные, компонентные и сквозные тесты.

### Последующие вертикальные этапы

1. Каталог персонажей и редактор.
2. Расширяемые визуальные состояния и генерация спрайтов.
3. Авторский сюжетный граф и инструменты проверки.
4. Полноэкранные CG-сцены и галерея.
5. Свободная новелла.
6. Обучение LoRA и управление визуальными профилями.
7. OpenAI и другие облачные провайдеры.
8. Звук, озвучка, локализация и расширенные инструменты автора.

Спецификация описывает целевую архитектуру, но первый план реализации не должен пытаться построить все этапы одновременно.

## 4. Общая архитектура

```text
React + Feature-Sliced Design
              |
              | HTTP/JSON
              v
FastAPI modular monolith
  |-- stories / sessions / story_engine
  |-- characters / visual_states
  |-- providers / generation_jobs
  |-- authoring / validation
  `-- SQLite + asset storage
              |
              | adapters
       +------+----------------+
       |                       |
     Ollama                 ComfyUI
   fast narrative      images and workflows
                               |
                         training worker
```

FastAPI — модульный монолит. Модули имеют явные сервисные границы, но разворачиваются одним локальным приложением. Фоновый worker запускается отдельным процессом, чтобы обучение и генерация не блокировали HTTP-сервер.

## 5. Backend

Рекомендуемая структура:

```text
app/
  main.py
  core/
    config.py
    errors.py
    lifespan.py
  db/
    session.py
    models.py
    migrations/
  modules/
    stories/
    sessions/
    story_engine/
    characters/
    visual_states/
    providers/
    generation_jobs/
    authoring/
  integrations/
    ollama/
    openai/
    comfyui/
```

В каждом бизнес-модуле допускаются `router`, `schemas`, `service` и `repository`, когда они действительно нужны. Правила:

- router занимается HTTP, а не бизнес-решениями;
- service выполняет сценарий использования и владеет транзакцией;
- repository изолирует доступ к данным;
- Pydantic/SQLModel используются на границах и для хранения;
- блокирующий локальный I/O выполняется синхронными `def`-обработчиками либо выносится в worker;
- зависимости FastAPI оформляются через `Annotated[..., Depends(...)]`;
- запуск и завершение ресурсов — через `lifespan`;
- изменение схемы SQLite — только миграциями Alembic;
- `main.py` остаётся точкой сборки, а не местом бизнес-логики.

## 6. Frontend

Frontend следует Feature-Sliced Design v2.1 и начинает с минимальных слоёв:

```text
src/
  app/       # router, providers, global styles
  pages/     # complete screens and page-local logic
  shared/    # shadcn UI, API client, config, generic utilities
```

Начальные страницы:

- `novel-library`;
- `story-setup`;
- `story-player`;
- `character-catalog`;
- `character-editor`.

`entities/character` появляется только после фактического использования модели персонажа несколькими страницами. `features` создаются для действительно повторяемых пользовательских действий. `widgets` не используются без убедительной причины. Каждый slice экспортирует публичный API через `index.ts`; импорты разрешены только из нижних слоёв. Структура проверяется Steiger.

## 7. Провайдеры ИИ

Провайдеры разделяются по возможностям, а не объединяются в один универсальный интерфейс.

### LLMProvider

```text
health_check()
list_models()
generate_turn(TurnRequest) -> TurnProposal
```

Первые реализации:

- `OllamaProvider` — локальные модели, первый этап;
- `OpenAIProvider` — официальный OpenAI API, последующий этап.

Подписка ChatGPT не является способом оплаты OpenAI API. OpenAI-провайдер использует отдельный API-ключ. Ключ не хранится в SQLite и не передаётся браузеру: в разработке он читается из окружения, а в desktop-сборке — из системного хранилища секретов.

### ImageProvider

Отвечает за черновую и финальную генерацию изображений. Первая реализация — ComfyUI. Контракт принимает нормализованное задание, а не внутренний JSON конкретного workflow.

### TrainingProvider

Создаёт задания обучения и сообщает прогресс. Обучение выполняется отдельным worker и не запускается внутри процесса FastAPI.

### Профили качества

- `narrative_fast` — обычные игровые ответы;
- `narrative_quality` — подготовка сложных сцен и сюжета;
- `image_preview` — быстрый черновик;
- `image_quality` — финальный спрайт или CG;
- `training` — обучение LoRA.

История может переопределить глобальный профиль и модель. Доменный движок работает только с `TurnRequest` и `TurnProposal`, поэтому смена провайдера не меняет правила игры.

## 8. Модель новеллы и сюжетный граф

Авторская новелла содержит:

- метаданные, рейтинг и версии;
- world bible;
- главы;
- персонажей и допустимые роли героя;
- узлы событий;
- условия входа;
- последствия;
- приоритеты;
- обязательные и необязательные события;
- границы свободы ИИ;
- режиссёрские указания;
- концовки.

Граф развивается инкрементально. Узел события не обязан содержать весь текст сцены: он задаёт канонический смысл, условия и разрешённые последствия. ИИ формирует конкретное повествование внутри этих границ.

Все authored-объекты получают стабильные UUID: сцены, события, реплики, выборы, переменные, CG, аудио и концовки. Отображаемые названия не используются как ключи.

## 9. Прохождение и транзакция хода

`story_session` фиксирует историю, версию контента, героя, провайдера, модель, текущую ветку и каноническое состояние.

Ход выполняется так:

1. Клиент отправляет действие, `request_id` и ожидаемую версию состояния.
2. Сервер загружает сюжет, память, персонажей и допустимые события.
3. Story engine строит нормализованный `TurnRequest`.
4. LLM возвращает `TurnProposal`.
5. Pydantic проверяет структуру.
6. Story engine проверяет персонажей, визуальные состояния, события и последствия.
7. Принятый ход, последствия и новая контрольная точка записываются одной транзакцией.
8. Повторный `request_id` возвращает уже созданный результат.
9. Клиент показывает подтверждённый текст и визуальное состояние.

Пример результата:

```json
{
  "narration": "Описание происходящего",
  "dialogue": {
    "character_id": "akane",
    "text": "Реплика Аканэ"
  },
  "visual_directive": {
    "mode": "sprite_scene",
    "emotion": "suspicion",
    "pose": "fan_open",
    "outfit": "red_dress"
  },
  "suggested_choices": [],
  "proposed_effects": []
}
```

Исходный ответ модели хранится отдельно от принятого хода вместе с моделью, версией промпта, длительностью и журналом исправлений. Он не является каноном.

## 10. Память

Контекст модели собирается из отдельных слоёв:

- неизменяемые факты мира;
- канонические факты прохождения;
- знания конкретного персонажа;
- отношения;
- активные цели и незавершённые события;
- резюме старых глав;
- последние полные ходы.

Старые события периодически сворачиваются в резюме, но исходные ходы не удаляются. Резюме содержит ссылки на факты-источники и проходит проверку на противоречия. Бюджет контекста зависит от модели и профиля провайдера.

## 11. Временная линия, сохранения и метапрогресс

Каждый подтверждённый ход создаёт неизменяемый checkpoint. Откат перемещает текущий указатель назад. Новое действие после отката создаёт новую ветку, а не уничтожает прежнюю.

```text
checkpoint 1 -> checkpoint 2 -> checkpoint 3
                                  |-- branch A
                                  `-- branch B
```

Поддерживаются:

- автосохранение после принятого хода;
- ручные слоты;
- быстрые сохранения;
- скриншот, глава, игровое время и дата в метаданных;
- история реплик;
- откат;
- повторная генерация как новая ветка;
- восстановление после аварии.

Отдельное постоянное хранилище содержит просмотренные строки, открытые CG, концовки, достижения, настройки и каталог персонажей. Эти данные не откатываются вместе с прохождением.

Сохранение содержит версии движка, новеллы, схемы состояния, промпта и ревизии персонажей. Обновлённая новелла либо мигрирует сохранение, либо продолжает его на закреплённой версии контента.

## 12. Персонажи

Основные сущности:

- `characters` — стабильная идентичность и происхождение;
- `character_revisions` — изменяемая версия профиля;
- `character_assets` — визуальные и звуковые материалы ревизии;
- `story_characters` — участие конкретной ревизии в новелле;
- `session_character_state` — память, отношения и состояние в прохождении.

Персонаж хранит имя, явно указанный возраст, признак совершеннолетия, местоимения, описание внешности, характер, речь, биографию, границы поведения и визуальный профиль.

При извлечении из новеллы создаётся редактируемый fork с сохранением источника, автора и родительской ревизии. В другой новелле персонаж по умолчанию начинает без старых воспоминаний и отношений. Позднее пользователь сможет переносить выбранные воспоминания явно.

## 13. Материалы персонажа

Типы материалов:

- `avatar` — квадрат 1:1 для списков и диалогов;
- `cover` — широкая обложка 16:9;
- `portrait` — крупный портрет;
- `sprite` — полноразмерное изображение с прозрачностью;
- `reference` — эталон для сохранения идентичности;
- `lora` — обученные веса;
- `voice_sample` — эталон голоса в будущем.

```text
data/characters/{character_id}/{revision_id}/
  avatar.webp
  cover.webp
  portrait.webp
  references/
  sprites/
  lora/
  voice/
```

В базе хранятся тип, путь, размеры, формат, хеш, описание, параметры кадрирования, происхождение и лицензия. Пропорции изображения никогда не исправляются растягиванием; используются crop/contain и производные размеры.

## 14. Визуальные состояния

Состояние не ограничивается фиксированными шестью эмоциями:

```text
emotion + pose + outfit + accessories + effects
```

Авторская сцена может принудительно задать состояние. В остальных случаях LLM предлагает его, а движок проверяет доступность. Комбинации кешируются.

Fallback:

1. точная комбинация;
2. без эффектов и необязательных аксессуаров;
3. та же эмоция с базовой позой;
4. нейтральное состояние в текущей одежде;
5. основной нейтральный спрайт.

Отсутствующее состояние не блокирует игру и может породить фоновое студийное задание.

## 15. Полноэкранные CG-сцены

Визуальная директива поддерживает:

- `sprite_scene` — фон и отдельные спрайты;
- `cg_scene` — цельная полноэкранная иллюстрация;
- в будущем `cinematic_sequence` — последовательность кадров или видео.

CG используется для объятий, поцелуев, боёв, сложных взаимодействий, необычных ракурсов, кульминаций и других сцен, которые плохо передаются спрайтами.

Авторские ключевые CG готовятся заранее. Уникальные изображения свободной новеллы создаются асинхронно: игрок может продолжить без ожидания, а готовый результат появляется в галерее. Для нескольких персонажей задание фиксирует ревизию каждого участника, одежду, позу, область изображения, референсы, LoRA, workflow, prompt, seed и модель. Региональное кондиционирование снижает смешивание внешности персонажей.

## 16. LoRA и постоянство внешности

Первый профиль обучения рассчитан на RTX 5080 16 ГБ:

- SDXL-совместимая аниме-модель как основной практичный вариант;
- FLUX как более тяжёлый экспериментальный профиль;
- кеширование латентов, gradient checkpointing, mixed precision и 8-битный оптимизатор;
- batch size и разрешение подбираются контрольным прогоном.

Визуальный профиль содержит эталоны, обучающий набор, подписи, базовую модель, trigger phrase, параметры обучения, контрольные prompts/seeds и статус версии. LoRA персонажа учит постоянные черты; стиль новеллы и сложные костюмы могут быть отдельными адаптерами.

Новая LoRA проходит фиксированную контрольную сетку ракурсов, эмоций, поз и одежды. Только вручную утверждённая версия становится основной. Неудачные результаты не добавляются в обучающий набор автоматически.

## 17. Студийные задания и GPU

Состояния задания:

```text
queued -> running -> review_required -> approved
                     |                 
                     `-> failed / cancelled
```

Локальный диспетчер GPU сериализует тяжёлые операции. Приоритеты:

1. активный игровой ответ;
2. быстрый preview по явной команде;
3. финальная генерация;
4. обучение.

Во время активной игры тяжёлая задача не стартует автоматически. Она остаётся в очереди либо приостанавливается в безопасной точке. FastAPI только управляет заданиями; worker владеет длительным процессом и прогрессом.

## 18. Режиссура, звук и управление чтением

Сцена может задавать фон, освещение, позиции, переходы, эффекты, движение камеры, музыку, звуки и голос. Музыка, SFX и голос имеют отдельные каналы и регуляторы громкости.

Игроку доступны:

- скорость появления текста и «Показать полностью»;
- авто-продолжение;
- пропуск только прочитанного либо всего текста по отдельной настройке;
- история реплик;
- скрытие интерфейса;
- повтор последней голосовой реплики;
- полноэкранный просмотр CG;
- галерея;
- отключение переходов и визуальных эффектов.

## 19. Локализация и доступность

Интерфейс и первый контент создаются на русском. Все строки интерфейса централизуются, а authored-реплики получают стабильные ID. Архитектура допускает перевод текста, изображений с надписями и озвучки.

Минимальные требования доступности:

- полная клавиатурная навигация;
- видимый focus;
- масштабирование текста и интерфейса;
- достаточный контраст;
- режим уменьшенного движения;
- альтернативные описания CG;
- подготовка текста для системного TTS;
- настройки скорости текста не влияют на доступность элементов управления.

## 20. Контент 18+

Новелла имеет рейтинг и набор тегов: нагота, сексуальный контент, кровь, жестокость, хоррор и другие. Пользователь видит предупреждение до запуска и может задать личные ограничения.

Локальные провайдеры могут обслуживать взрослый контент без автоматического смягчения. Облачный провайдер обязан объявлять свои возможности и ограничения; движок не переписывает сцену незаметно, а сообщает о несовместимости и предлагает доступный локальный вариант.

Сексуальный контент допускается только для явно совершеннолетних персонажей. Проверка выполняется до вызова текстового или графического провайдера. Смена формулировки не обходит это правило.

## 21. Инструменты автора и lint

Редактор и CI-проверка должны выявлять:

- недостижимые узлы и концовки;
- тупики и циклы без выхода;
- выборы без допустимого продолжения;
- отсутствующие ресурсы, персонажей и локализации;
- неизвестные переменные и неверные типы;
- конфликтующие последствия;
- несовместимые визуальные состояния;
- нарушение возрастных ограничений;
- потерянные стабильные ID;
- несовместимость версии сохранения.

Симулятор проходит граф с разными состояниями, позволяет перейти к узлу, изменить переменные и воспроизвести путь. Lint дополняет, но не заменяет тестирование и ручное прохождение.

## 22. Ошибки и восстановление

- При недоступности LLM управление блокируется, показывается причина, повтор и переход к настройкам.
- Шаблонный сюжетный ответ не подставляется вместо нейросети.
- Повреждённый JSON один раз отправляется модели на исправление формата; повторная неудача отклоняет ход.
- Недопустимые последствия не применяются.
- Ошибка не меняет каноническое состояние.
- Неудачная графическая задача допускает повтор и сохраняет диагностические метаданные.
- Незавершённые задания восстанавливаются либо корректно помечаются после перезапуска.
- После аварии предлагается последний подтверждённый checkpoint.

Пользовательские сообщения — на русском и содержат действие, которое можно предпринять. Техническая причина доступна отдельно.

## 23. Приватность, безопасность и происхождение материалов

- Секреты не попадают в SQLite, браузер, промпты и логи.
- По умолчанию истории, изображения и обучающие наборы остаются локальными.
- Перед обращением к облаку интерфейс сообщает, какие данные будут отправлены.
- Логи не содержат полный чувствительный контент без включённого диагностического режима.
- Каждый импортированный или созданный материал хранит источник, автора, лицензию и хеш.
- Экспорт персонажа включает manifest и выбранные материалы, но не переносит секреты провайдеров.
- База и пользовательские материалы поддерживают резервное копирование и проверку целостности.

## 24. Тестирование

### Backend

- правила сюжетного графа и последствия;
- Pydantic-контракты провайдеров;
- повреждённые и противоречивые ответы;
- идемпотентность `request_id`;
- optimistic concurrency по версии состояния;
- атомарность SQLite;
- rollback, ветвление и миграции сохранений;
- память и обнаружение противоречий;
- возрастные ограничения;
- зависимости и восстановление фоновых заданий.

### Frontend

- русские состояния страниц;
- клавиатурная навигация;
- блокировка и восстановление управления;
- постепенный показ текста;
- история, сохранение и откат;
- fallback визуальных материалов;
- настройки доступности.

### Сквозные сценарии

1. Запуск истории с Аканэ.
2. Выбор или свободное действие.
3. Ответ Ollama, проверка и сохранение.
4. Смена реплики и спрайта.
5. Перезапуск приложения и восстановление.
6. Откат и создание второй ветки.
7. Недоступность Ollama без повреждения прохождения.

### Визуальное качество

Каждая версия LoRA и workflow прогоняется на фиксированной матрице seed/prompt. Человек проверяет лицо, телосложение, цвета, одежду, различимость персонажей, руки и соответствие стилю.

## 25. Критерии готовности первого этапа

- Текущий UI перенесён на согласованную FSD-структуру и проходит Steiger.
- FastAPI разбит на минимальные модули без бизнес-логики в router.
- Ollama подключена через `LLMProvider` и health check.
- Ход имеет строгий контракт, серверную валидацию, idempotency и атомарное сохранение.
- История Аканэ поддерживает варианты и свободное действие.
- Существующие спрайты меняются по подтверждённой визуальной директиве.
- При недоступности модели управление блокируется с понятным восстановлением.
- Приложение восстанавливает последнее прохождение после перезапуска.
- Backend tests, frontend tests, lint, typecheck и production build проходят.

## 26. Отложенные решения

Конкретные SDXL/FLUX checkpoints, trainer и ComfyUI workflows выбираются отдельным исследованием с проверкой качества, лицензии и производительности на RTX 5080. Аналогично отдельно проектируются UI редактора графа, TTS/voice cloning, формат внешних пакетов новелл и desktop-упаковка. Эти решения не должны блокировать первый игровой цикл.
